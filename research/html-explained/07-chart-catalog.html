07 / Chart catalog

Start with the ladder, then add families.

The system is designed to grow beyond line and area, but chart breadth is a downstream track. Each future family needs its own rung semantics, plan snapshots, renderer, accessibility rules, and browser proof.

Current truth. planChart() resolves line and area. The catalog below describes the intended product surface and marks the rest as planned.

Line and area share one ladder.

Line

One or more series rendered as paths. It can become a single value, sparkline-like strip, readable axes, points, direct labels, legend, and stage annotations as space permits.

Core contract: ChartType = 'line' and the six LINE_RUNGS.

implemented

Area

Uses the same size-family decisions as line but exposes an area treatment for the primary mark. Negative values matter more because the baseline is visually asserted.

Core contract: ChartType = 'area' and the same line rung functions.

Chart-family template

How a new chart gets added.

Every future family should repeat the same work. That repetition is a feature: it prevents a new renderer from bypassing the system’s central promises.

D1 / semantics

Write a complete ladder

Define each rung as a full state. Include small-only additions, replacements, aggregation rules, and what the chart claims about value legibility.

D2 / contract

Map it to ChartPlan

Use existing fields where the meaning is shared; add a typed field only when the family introduces a genuinely new state.

D3 / resolver

Implement policy-backed planning

No bare thresholds in a rung. Every decision is typed, tiered, serialisable, and consumed by the planner.

D4 / renderer

Add primitives and data frame

Keep geometry in core, markup in primitives, and interaction in the client package. Use CSS-settable geometry for token-controlled values.

D5 / proof

Snapshot, browser, accessibility

Test the ladder, the semantic element set, server rendering, containment, reduced motion, and the interaction path the family actually needs.

Selection guide

Pick a family from the question.

The data shape matters, but the reader’s question comes first. This is a product decision aid, not a complete recommendation engine.

How is it changing?

Line / area for a continuous or time-indexed trend. At tiny sizes, say the latest value and direction instead of drawing a dishonest micro chart.

How do parts compare?

Bar for discrete categories; donut only when part-to-whole composition is genuinely the question and the category count stays scannable.

Do two variables relate?

Scatter. Keep point identity, axes, and outlier labeling explicit; change renderer for performance rather than silently dropping observations.

Where does a process leak?

Funnel, with stage names and drop-off semantics. Horizontal orientation is often more honest when height is limited.

What is the current number?

KPI / number for the primary value. Add a delta, basis, and a compact trend only when they fit the information budget.

Which cells are active?

Heatmap for repeated categorical/time cells. Aggregate by an explicit unit when cell size becomes unreadable.
