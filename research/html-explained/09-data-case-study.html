09 / Dataset + case study

Give the library a real question.

A dataset turns the architecture into something you can inspect. It lets us see which chart family fits, how the ladder changes the story, how long labels behave, and where the current implementation is still a prototype.

Case-study promise. We will show the problem, the evidence, the design decision, the code path, and the limitation. We will not invent product impact or claim a shipped chart family that the repo does not implement.

A useful first application

Defence procurement readiness.

This is a proposed dataset shape for understanding the library, not a claim about a real customer or real operational data. It is useful because it has time, categories, thresholds, comparisons, and clear sensitivity boundaries.

Dataset contract

Shape data for the reader’s question.

Start small enough to understand and rich enough to break the planner. Keep raw facts separate from display decisions.

type ReadinessPoint = {
  period: string       // ISO month: "2026-01"
  value: number | null // missing is explicit
  target?: number
}

type Series = {
  id: string
  label: string
  points: ReadinessPoint[]
}

const dataset = {
  title: 'Readiness by program',
  unit: '%',
  series: [
    { id: 'air', label: 'Air Defence Modernisation', points: [...] },
    { id: 'naval', label: 'Naval Sustainment', points: [...] },
  ],
}

const shape = {
  seriesCount: dataset.series.length,
  pointCount: dataset.series[0].points.length,
  hasNegative: false,
}
→

Dataset rule: missing is not zero. If an application cannot distinguish “no activity,” “not measured,” and “not applicable,” the chart cannot tell the reader those meanings apart either.

Case-study structure

Tell the story in evidence order.

Use this outline for a portfolio case study, internal review, or project handoff. Each section should answer one question and link to the code or fixture that proves it.

01 / context

What was hard?

One responsive widget has to survive many information budgets without confusing “visible” with “readable.”

02 / evidence

What did we observe?

Show the size sweep, label collisions, plot-height constraints, and containment risk. Label measured results separately from interpretation.

03 / decision

What did we choose?

Adopt a six-rung ladder, a complete serialisable ChartPlan, no DOM measurement in core, and explicit package boundaries.

04 / build

How does code express it?

Walk from sizeContextFromPixels through planChart, resolveFrame, and the SVG primitives.

05 / result

What can we claim?

Current line/area behavior, generated themes, deterministic metrics, and the verified gates. Keep planned families and external impact labeled as next or unverified.

Questions for the next data handoff

What you can give me later.

When you have real application data, use these prompts so the next chart can be designed from evidence.

  1. What is the reader trying to decide?
  2. What is the primary measure and its unit?
  3. What is the time/category grain?
  4. Which missing values are possible and what do they mean?
  5. What are the important thresholds or comparison bases?
  1. How many series or categories can appear?
  2. Which labels can be long, localized, or multilingual?
  3. Which values are sensitive and can be safely shown in a case study?
  4. What screenshots or source exports can prove the current state?
  5. What outcome is measured, and what remains an inference?
