04 / Planner

Size becomes a plan.

The resolver does not squeeze a full chart into every box. It classifies the box, chooses a complete rung specification, lays out the inside of the box, then lets the renderer draw that result.

The responsive ladder

Information enters and leaves deliberately.

These families are named after information budget rather than a single pixel breakpoint. The current implementation has a full line/area ladder.

The plan object

Every field states what exists.

A plan is not a list of instructions like “hide the legend when small.” It is a complete state at one rung: what is visible, where it lives, and what it is allowed to claim.

valueLegibility

single-value means there is no readable plot; shape-only means the trend is shown without claiming precise value reading; values means axes must support estimation.

axes

Each axis says whether it is visible, has a domain line, what tick mode it uses, whether it has a title, and whether it draws gridlines.

marks

The current line/area ladder can choose a line, an area fill, a horizon band, or no plot. Points are none, extrema, or all.

labels

Label policy is explicit: none, endpoints, direct, or full; axis labels can degrade through abbreviate, split, rotate, and transpose.

legend

Placement is state, not a boolean. It can be absent, internal, external, or another explicit composition; this keeps small-to-large behavior invertible.

motion

Motion describes the transition class and duration. Reduced motion is handled by CSS, not by a hidden plan flag that could change server output.

High-level source route

Follow this when reading the code.

The resolver’s sequence is load-bearing. A later decision must not feed back into the size of the box that produced it.

const ctx = sizeContextFromPixels(width, height)
const shape = describeShape(data)

// plan-chart.ts
const sizeClass = resolveSizeClass(ctx.cols, ctx.rows)
const rung = LINE_RUNGS[sizeClass]
const plan = rung({ type, ctx, shape, policy: resolvePolicy(policy) })

// layout.ts: one-way, stable order
const plot = resolvePlotBox(plan, ctx)

// frame.ts: only here do values enter geometry
const frame = resolveFrame(plan, data, plot)

// primitives: render plan + frame; do not make new semantic choices
!

Why single pass? Y-label width influences the y gutter, which influences plot width, which influences x ticks, which influences x labels. Letting x-label decisions feed back into y-label decisions would create a fixpoint inside a resize callback.

From plan to pixels

There are two separate transformations.

Keeping them separate makes the system easy to reason about: first decide the composition, then place actual values inside the spaces that decision reserved.

semanticPlan“Panel, line mark, y-axis with 4 ticks, direct labels, no external legend.”
geometricFrame“This value is x=138, y=72; this tick is y=105; this path is d=…”

What the renderer receives

Chart receives a plan, canonical series data, and the computed frame/geometry path available through core. It emits semantic groups such as gx-axis, gx-line, gx-point, labels, and an optional data table.

Honesty checks

The planner’s important invariants.

These are the checks worth understanding before you change a threshold or add a chart family.

AValue legibility gates axes. If the plan does not claim values, the y-axis cannot be visible.
BHorizon is a replacement. Under the plot-height floor, the mark changes encoding instead of becoming a tiny line.
CPlans are JSON-safe. No undefined, functions, Date, Map, Set, NaN, or Infinity.
DSize is memoryless. Sweeping width up or down must produce the same plan at the same size.

Unsupported types fail loudly

The public ChartType union includes the planned catalog, but today planChart() resolves only line and area. Unsupported types throw with the milestone that would add them. Silent fallback would make a consumer think the requested chart rendered when it did not.
