Start here / no jargon first

One chart that changes its answer to fit the space.

This project is a chart library for dashboards. The same chart can live in a wide card, a short strip, or a tiny tile. Instead of squeezing the full chart until it becomes unreadable, it chooses a simpler, honest version.

In one sentence: your app gives us data, the dashboard gives us a box, the library decides what can fit, and the chart draws that decision.

The problem statement

A chart is not useful just because it fits.

Dashboards give every card a different amount of room. A normal chart often keeps all its labels, axes, and decorations and simply makes them smaller. That technically fits, but a person can no longer read it or trust what it is saying.

The problem

Everything gets squeezed.

Labels collide, legends wrap, values disappear, and the reader has to guess what the picture means.

The design question

What is still useful here?

When space changes, which parts should remain, which parts should be removed, and what can the chart honestly claim?

Our answer

Change the information level.

Keep the same underlying data, but move through planned sizes: full explanation → trend → headline answer.

One case study

Let’s follow equipment readiness.

Imagine a defence dashboard asking: “Are our programmes getting closer to the 80% readiness target?” We will use the same tiny dataset through every step so the transitions are easy to see.

The data does not change

What the application gives the chart

ProgrammeJanFebMarApr
A72%76%79%84%
B64%68%67%73%
C88%86%91%93%
Target: 80%. The person reading the dashboard wants a quick, truthful answer about progress toward that target.
The library’s job

Turn the same facts into the right amount of detail.

01Wide card: show the series, readable axes, target line, legend, and enough detail to compare programmes.
02Short card: keep the trend shape, but remove a y-axis that would be too cramped to read.
03Tiny card: show “84% / up 5 points” instead of pretending a tiny plot can support exact reading.

Boundary: the application owns the readiness numbers. GX only chooses their presentation.

The important part: the library is not hiding information randomly. It follows a written order of priorities. Every size has a meaning.

The flow map

What happens when someone resizes the card?

Here is the complete journey in everyday language. Read left to right: each box receives something, does one job, and passes a clear result forward.

1. The user drags the cardThe dashboard box changes from, for example, 480×280 pixels to 220×120 pixels.
new size
2. The sensor noticesA browser helper called ResizeObserver reports the new width and height.
ask again
3. The planner choosesCore selects the right size family and writes a new ChartPlan.
4. The plan says what existsIt can say: show a line, hide the y-axis, keep the latest value, and use a tap interaction.
follow plan
5. Drawing pieces renderPrimitives turn those instructions into accessible SVG. They do not make a second decision.
apply look
6. Tokens style itColors, fonts, spacing, lines, and dark/light appearance are applied without changing the meaning.
↻

Then the loop repeats. If the box changes again, the same data goes through the same steps and may receive a different plan.

Two ways to render

The same plan can work on a server or in a browser.

This is why the system is split into layers. A static chart can be included in HTML before the browser runs. An interactive chart can measure its box and repeat the planning loop.

server-safe path / stable HTML

When the size is already known

Your app supplies a size, core makes a plan, and primitives return SVG. There is no browser sensor in this path.

data→core plan→SVG

Useful for: server rendering, exports, tests, and pages that should arrive with a chart already present.

browser path / responsive behaviour

When the size can change

React observes the card, sends the new size to core, and passes the new plan to the same primitives.

data+box sensor→plan→SVG

Useful for: draggable dashboards, responsive pages, and cards that change with a window or side panel.

Themes, tokens, and fonts

Why are there so many visual names?

A theme is a complete visual recipe. Tokens are the named ingredients inside that recipe. We keep them separate so an application can change its look without changing what the chart claims.

Theme = a whole recipe

Dark, light, Rail, Neutral

The shipped scopes are Rail dark, Rail light, Neutral dark, and Neutral light. They share the same chart API but use different surfaces, series colors, contrast, radius, and shadows.

Why: an application can adopt the visual language that fits its product.

Token = one named ingredient

Not just “blue” and “grey.”

There are separate names for the plot ground, border, each series, axis, grid, label, line width, gap, motion, tooltip, and more.

Why: one decision can be changed once and remain consistent everywhere.

Policy = meaning

Some choices cannot be CSS-only.

Changing a gridline color is appearance. Deciding whether a y-axis is visible changes what a reader can claim from the chart, so that choice stays in the planner’s typed policy.

Why: a theme should not silently change the answer.

Simple analogy: the plan decides what is on the plate; the theme decides the color of the plate. A prettier plate must not add food that the plan did not ask for.

Fonts are part of the layout

Why can’t every font be treated as interchangeable?

Words take up space. If the planner measures one font but the browser draws another, a label can look safe in the calculation and collide on screen. That is why the first supported reference family is deliberate.

Current font contract

  • Reference family: Roboto Flex, with a system fallback stack.
  • Five ranks: A–E, from the most important title to the smallest supported detail.
  • Smallest rank: about 10px; normal chart labels are about 11px; titles are about 12–13px.
  • Measured settings: size, weight, optical sizing, letter spacing, and numeric features must agree between planning and CSS.

This is a safe starting point, not a claim that other fonts are impossible.

What adding a font means

  1. Measure its character widths for each supported rank.
  2. Use the same weight, spacing, and optical settings in the browser.
  3. Carry those metrics with the planner’s typography input.
  4. Run collision, accessibility, and browser checks again.

Plain English: choosing a different font is partly a visual choice and partly a geometry choice.

Known lettersCommon Latin labels and symbols use measured advances.
Wide lettersCJK and full-width characters use a conservative wider fallback band today.
Safe directionIt is better to degrade early than let text collide and look trustworthy when it is not.

For someone downloading the package

How would you use and theme it?

The consumer should provide data and a chart type. The library should provide the responsive decisions. The visual override should be explicit and scoped to the consumer’s application.

1 / render a chart

Conceptual consumer code

import { AutoChart } from '@gx/react'
import '@gx/tokens/theme.css'

<section data-gx-theme="neutral-light">
  <AutoChart
    type="line"
    data={readiness}
    title="Equipment readiness"
  />
</section>

The exact package entry points are documented in 08 / Consumer guide. The important idea is the boundary: data in, responsive chart out.

2 / change the look

Override named visual values

/* Your application CSS */
.mission-dashboard {
  --gx-surface-color: #101820;
  --gx-axis-color: #d7e8ef;
  --gx-line-stroke-width: 2px;
}

/* Use the same token names; do not edit chart internals. */
.mission-dashboard[data-gx-theme="neutral-light"] {
  --gx-ground: #f7f5ef;
}

Theme rule: colors, spacing, stroke, type presentation, and motion can be changed. If a new font changes text widths, it needs a matching metrics configuration too.

What the user does not need to do: write a resize listener, hand-code five chart versions, or decide which axis to hide in every screen size. That is the library’s job.

Rules that protect the idea

What we deliberately refuse to do.

These rules stop the project from becoming a pile of chart-specific shortcuts. They are the reason the same story can be explained, tested, and reused.

No hidden browser work in coreThe planner can run without the DOM, React, or a live browser.
No content-sized outer boxThe dashboard gives the box. The chart must fit inside it, not secretly resize the dashboard.
No styling that changes meaningCSS can change appearance. Plan policy decides information and legibility.
No silent unsupported fallbackIf a chart family is not ready, the system should say so instead of pretending.
No tiny chart pretending to be preciseWhen exact reading is not possible, the visual changes to a headline or a trend.
No “works on my screen” proofSize families, server output, accessibility, themes, and real browser transitions all need checks.
