01 / Start here

The box is small. The decision is not.

GX is a chart and dashboard-grid library for interfaces where the same widget can be resized from a one-cell glance to a full analytical stage.

Problem statement. Given a chart, its data shape, and the measured box, decide what information can be shown honestly at that size, then render that decision consistently on server and client.
Failure we are avoidingfixed chart → shrinking box

The fixed chart problem and the responsive ladder are specified in research/10-responsive-ladder.md.

Why normal responsive charts fail

Smaller is not a strategy.

A dashboard can give the chart less width, less height, fewer pixels, and less attention. The right response is not always to scale every mark and label down.

Readability collapses

Axes, labels, legends, and values compete for the same small plot. A chart can still be technically visible while making a false promise: “you can estimate values here.”

Meaning disappears

A dense chart may remove labels randomly or truncate the legend. The reader cannot tell whether missing information was intentionally aggregated, accidentally clipped, or never loaded.

Resize becomes unstable

If content changes the measured box, ResizeObserver can feed a new size back into the chart. The chart then changes the size that caused the decision. That loop is an architectural failure.

The product thesis

What GX promises.

Every promise becomes a type, a boundary, a test, or an explicit limitation. The library is small because each layer is narrow.

01

The grid owns the box. It positions, drags, and resizes widgets. It does not decide which marks or labels appear.

02

Core owns the meaning. A pure resolver turns size + data shape + policy into a complete serialisable ChartPlan.

03

The renderer owns pixels. Hook-free primitives draw the plan into accessible SVG without re-deciding its semantics.

04

Tokens own presentation. Themeable CSS custom properties change visual language without changing the plan’s meaning.

The contract

A chart is a decision, not a shape.

The central object is a plan. It is deliberately complete at every rung, so “what happens when the box grows?” is data the tests can inspect.

type DecisionInput = {
  type: ChartType
  size: SizeContext
  shape: DataShape
  policy?: Partial<PlanPolicy>
}

const plan = planChart(input.type, input.size, input.shape, input.policy)

// plan is plain JSON: no DOM nodes, functions, Date, Map, or Set.
// The renderer can now draw exactly what the resolver decided.

Case-study lens

How to explain this project honestly.

The strongest case study is not “we made charts.” It is the sequence of constraints and decisions that make a responsive chart trustworthy.

Evidence

Small chart boxes create label collisions, value-estimation problems, and resize containment risk.

Insight

Responsive behavior needs a semantic ladder: replace, simplify, degrade, and only then add detail.

Decision

Make the ladder explicit in a serialisable plan and keep the grid, planner, renderer, and theme layers separate.
