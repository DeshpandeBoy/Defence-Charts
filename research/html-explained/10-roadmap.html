10 / Roadmap

Build the proof in the right order.

The roadmap is not a feature wishlist. It is a sequence of contracts: first make the planner honest, then make the renderer safe, then add the client boundary, then widen the chart catalog.

Current status. The line/area planner and the A/B tracks are substantially implemented in the repository. Grid integration, interaction, and additional chart families remain downstream work.

Milestone map

What is done, what follows.

Use the status tags as a reading aid, not as a release promise. “Complete” means the repository has the relevant implementation and tests; publishing and broader consumer proof are separate gates.

A1 / foundation
complete

Package boundaries and trust rules

Dependency direction, DOM ban, token gate, client-directive survival, and deterministic test setup.

A2–A3 / planner
complete

Responsive ladder and ChartPlan

Six size families, complete line/area rung specs, policy inputs, overrides, plot layout, label degradation, and invariants.

complete

Canonical data, scales, ticks, paths, points, axes, labels, values, tables, and RSC fixture proof.

implemented / verify continuously

AutoChart, resize, motion

ResizeObserver seam, containment checks, transition contract, reduced-motion behavior, and real-browser gates.

Suggested next working sessions

What to do after reading.

These are small enough to turn into concrete tasks and ordered so each one reduces uncertainty for the next.

1 / understand

Run the playground

Change the ladder, read the plan panel, inspect text metrics, and compare the rendered chart at Panel and Stage.

2 / stress

Feed the fixture matrix

Use long labels, 6 series, negative values, missing periods, and small heights. Capture plan JSON and screenshots.

3 / decide

Choose the first real application

Pick one reader question and a safe dataset. Do not start by choosing a chart type; start with the decision the reader needs to make.

4 / integrate

Try a scoped theme

Use Rail or Neutral first, then add only the overrides that your product can justify. Check contrast and token lint.

5 / verify

Run real browser gates

Check server output, ResizeObserver containment, transition frames, reduced motion, and the resting state.

6 / document

Write the case study

Use the evidence → insight → decision → build → limitation structure from the dataset page.

The finish line

Understandable, extendable, honest.

The project is successful when a new contributor can answer: where does this decision live, what data does it consume, what does the consumer control, and what proof says it works?

Where?

One package and one source file owns the decision.

What?

Plain data enters; a complete plan and accessible SVG leave.

Proof?

Tests, generated-output checks, and browser evidence distinguish implemented, planned, and unresolved.
