Product analysis translated into code

What changed in the way we build?

The research was useful because it changed ownership decisions. These are the rules that keep the library understandable as it grows.

shadcn lesson

Compose the surface

Use a chart shell plus optional pieces: config, tooltip, legend, loading, empty, error, and table. The shell organizes the experience; the planner still owns the chart answer.

Basedash lesson

Give the dashboard context

Quiet card chrome, generous space, a shared filter row above the grid, drag from the header, 12px gaps/padding, and a narrow one-column policy make the page feel like a dashboard rather than a pile of charts.

ownership rule

Keep three states separate

layoutState says where a widget lives. filterState says what the user is asking. dataState says what arrived. The host app owns fetching, filters, and persistence.

coordinate rule

Each layer owns one box

Dashboard → widget → plot → overlay. The grid owns the widget box. The chart divides that box. Tooltips and crosshairs sit out of normal flow. A chart never makes the dashboard grow by surprise.

open-source boundary

Free first, Pro later

Free means core, grid, basic interactions, and standard chart families. Advanced filters, linked views, brush/zoom, and one validated Pro capability come only after the public contracts are stable.

evidence rule

Research is not runtime proof

A proposal, a screenshot, and an upstream API note help us decide. They do not prove our package works. Every claim must eventually point to code, tests, packed consumers, or real-browser evidence.

Definition of done

When can we say “this is built”?

All of these must be true for the corresponding surface. A green card in the repository is not a green release by itself.

For a chart family

  • Plan: its data meaning and size ladder are explicit.
  • Render: SVG and table/fallback output agree with the plan.
  • Explore: tooltip, legend, keyboard, touch, and reduced-motion behavior are proven by the interaction matrix.
  • Evidence: empirical assistive-technology review is still tracked as CR-X04.

For the library release

  • Install: a fresh app can use the packed artefacts, not just source files.
  • Import: public exports, CSS, ESM, RSC, Vite, peer dependencies, and tree-shaking work.
  • Operate: layout migration and host-owned persistence still need the C3.2 contract.
  • Claim: docs describe what is shipped, what is experimental, and what is still planned.

The next exact sequence

What should happen next?

This order keeps the work small enough to review and strong enough to unlock the next step.

  1. Finish C3.2 layout serialization and migration.Wait for CR-C03, then define versioned round-trips, duplicate/missing-widget reconciliation, and host-owned save boundaries.
  2. Resolve P0.3: final public package name and npm scope.The package metadata and licence are prepared, but the placeholder @gx/* identity cannot be the final public promise.
  3. Run E2.1 and publish Preview.Apply the final name, add Changesets/trusted publishing, and release the already-proven dashboard slice.
  4. Run E3.1 Free-v1 claim and release audit.Audit the ten-family catalogue, packed consumer proof, accessibility evidence, docs, and every public claim before calling Free v1 released.
  5. Keep advanced product scope separate.Shared filters, linked views, brush/zoom, annotations, and one validated Pro capability remain v1.1/commercial work.

In one sentence: we are not just adding charts; we are building a dependable chain from data → plan → widget box → interaction → package → consumer proof.
